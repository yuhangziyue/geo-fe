P1

AI Visibility Dashboard

监测 → 诊断 → 行动 · 数据口径全部由明细重算 · 数字逐字可回查
问题

出题方给了 120 条真实观测（32 个 Prompt × 5 个 AI 平台 × 30 天）——品牌在 AI 助手的回答里被提及、被推荐、被引用的原始记录。要把它做成能指导行动的产品，而不是一堆图表。

策略

把「看数据」升级为监测 → 诊断 → 行动的闭环：漏斗与矩阵负责监测，词云 / 归因 / 趋势负责诊断，行动中心是行动出口。所有指标由明细重算、口径写在页面上，AI 摘要逐数字回查——整个产品只回答一个问题：下一步该改哪里。

核心决策 · 三条承重墙

决策 01

指标由明细重算，口径透明

不读 summary 文件：可见性 = 提及率、漏斗按行口径 120→85(71%)→56(47%)、取整用五成双——每个口径写在页面上，单测与出题方汇总逐项对账。

决策 02

AI 输出不信任，只验证

执行摘要每个数字回查事实集，对不上在页面标红；无 key 走确定性模板，mock 模式内置一个故意写错的数字用于演示标红。规则模板 16/16 全过，AI 输出可能带红。

决策 03

五态矩阵：未监测 ≠ 表现差

recommended / partly / mentioned-only / not-mentioned / not-tracked 用同色相明度递减——「未监测」与「表现差」不混为一谈，该改的是白洞不是深色格。

决策 04

趋势去噪：单日只有五档

一天一平台一问，单日可见性只能取 0/25/50/75/100，日线毛刺全是假信号——主线用 7 日滚动窗口，日值只作淡色散点；小多图 n<8 不画线，不造数据。

执行细节

筛选即 URL，时间锚定数据末日

平台 / Topic / 意图 / 时间窗全部进 URL，可分享可回放；回看窗口锚定数据截止日（Aug 30），杜绝「拿今天对比 8 月数据」的误导。

双视图信息层级

?tab= 拆出 Data（看结果：漏斗→矩阵→词云→平台|趋势→Topic|意图→信源）与 AI Insights（给行动方向：行动中心独占），状态在 URL。

视觉即信号

深墨信号台 + 全站唯一青色粗线（对比度 9.88:1）；「● LIVE · as of Aug 30」是静态截止戳，如实标注不装实时流；375px 响应式底线由 e2e 断言。

边界诚实

S 层无数据显示 Not tracked 而非 0%；自有来源 ⓘ 声明不冒充官方口径（自有域名是推断的，凡相关指标都带声明）。

数据形态（P1 无数据库表）：只读 project1_dashboard/dashboard_summary.json（对账用）+ questions.json（明细 = 真相源）。 所有指标由明细重算，加载时 zod 校验形状与行内业务规则（推荐必先提及、提到产品必算提及）；summary 文件只用来对账。

架构：JSON 明细 → 领域聚合 → API → 客户端渲染，LLM 适配独立成层

P2

AI 产品知识中心

数据是唯一真相源 · CMS → 实体 → 页面 → Schema 一条链 · 页面同时适合人、搜索引擎与 AI
问题

GEO（生成式引擎优化）的立论是：让 AI 系统能准确理解并引用站点内容。给出的是品牌 / 系列 / 产品 / FAQ 的原始 JSON——要让同一份内容同时服务人、搜索引擎与 AI。

策略

数据是唯一真相源：CMS → 实体 → 页面 → Schema 一条链。页面与 JSON-LD 渲染同一份 ProductDetail，SSG 预生成 + 保存后按需重生成——改数据，HTML 与结构化数据自然同步，不出现「页面改了、Schema 没改」的错位。

核心决策 · 三条承重墙

决策 01

数据是唯一真相源

Brand → Series → Product → FAQ 实体模型（SQLite + Drizzle，外键 + slug 唯一）；页面与 JSON-LD 渲染同一份 ProductDetail，改数据，HTML 与 Schema 自然同步。

决策 02

SSG 优先，按需重生成

generateStaticParams 构建时预生成完整 HTML（21 产品 + 8 场景）；后台保存 revalidatePath 只重渲染被改的页。爬虫和 AI 抓取拿到完整 HTML——GEO 的立论。

决策 03

不编造

JSON-LD 与页面可见内容同源；数据没有价格就不补 offers（Rich Results 报错是照实留档）；dateModified 只在有真实编辑时间时输出，不拿导入时间冒充。

执行细节

场景是实体，P1→P2 有桥

Topic 与场景从不同名，用人工映射表（6 个 Topic → 场景页）；看板「最弱 Topic」和问题详情直接链到该改的场景页——诊断与行动闭环。

Ask AI 边界诚实

只依据知识库回答；卖点与规格矛盾时两处引用并提示 Sources disagree，不替数据拍板；查不到明确说没有。

机器可读出口

sitemap.xml（只收录公开页）· robots.txt（隔离 dashboard/admin/api）· llms.txt（AI 爬虫地图，后台写后同步再生成）。

薄内容保护

空场景页 noindex、不进 sitemap / llms.txt、不输出 JSON-LD——空页对 SEO 和 GEO 都是薄内容，不如明确不收录。

后台 = 简化 CMS

zod 与数据文件共用同一份 schema 校验表单；保存即触发重新生成。规模上限（产品上万）时的演进路径（revalidateTag）已写在 README。

数据模型：SQLite + Drizzle，8 张表，slug 全库唯一

实体关系：Brand 1—N Series 1—N Product；Product 1—N Feature / AI Feature / FAQ / Best For；Scenario 可空关联（best_for 未匹配场景时保留为标签，不改变原始数据含义）。只有四张 product 子表的 product_id 外键带 ON DELETE CASCADE；brand_id / series_id / scenario_id 均不带（父行不在运行期删除）。

关键取舍：每个选择都写了反方

没有银弹，只有 trade-off。下面是两项目最重要的九个决策——备选了什么、为什么没选、什么条件下换道（完整版见 README §4）。

决策反方（没选什么）为什么不选何时换
P1指标由明细重算直接读 summary 汇总文件省事但口径不透明；数据源换成真实明细时接口要重写明细到百万行 → 按天/平台/Topic 预聚合，契约不变
P1摘要走规则模板 + 逐数字回查纯 LLM 生成，更「AI」模型可能编数字、评审无法复现；无 key 时演示不了有稳定供应商后换评测过的型号；回查升级为数字绑定事实路径
P1矩阵五态明度编码红绿黄信号色「未监测」和「表现差」混为一谈；红绿对色觉障碍不友好问题过百时默认只显示 Top-12
P1趋势主线用 7 日滚动直接画日值折线单日只有 0/25/50/75/100 五档，毛刺全是假信号单平台日问数上百时，日值有统计意义，回日线
P1自有来源按域名判定用数据方的 source_type=Official13 条 Official 引用只有 1 条在自有域名，混用会把占比算错拿到官方口径的域名清单后替换推断值
P2SSG + revalidatePath 按需重生成纯客户端渲染 / 每请求 SSRCSR 爬虫读不到（GEO 立论不成立）；SSR 对几乎不变的内容是浪费产品上万、一次编辑重生成页面太多 → revalidateTag 精确失效
P2JSON-LD 不补 offers / 评分补 mock 价格让 Rich Results 全绿编造价格违反结构化数据政策，也违背「不改原始数据含义」有真实价格 / 评价数据时补上，争取富摘要
P2Ask AI 用关键词检索向量检索 / 全部知识塞进提示词向量要嵌入模型或外部服务（评审跑不起来）；塞提示词没有检索依据、引用无从标起知识上千条、问法发散 → 关键词 + 向量混合检索，LLM 生成逐句标来源
P2best_for 完全匹配才链场景合并近似标签（Small Retail → Retail）改变了原始数据的含义，场景页饱满是假象内容团队确认分类后，由人在后台维护「标签 → 场景」映射表

跨项目共性设计准则

  • 数据是唯一真相源——页面、JSON-LD、机器出口全部从同一份数据渲染，不维护第二份真相
  • 边界诚实——不编造价格/日期/数据；局限在 README 与页面上如实标注
  • 测试断言全部来自人工核算——单测值是对着原始数据算出来的，不是抄实现
  • 无 key 可完整运行——LLM 缺 key 自动降级模板，不阻塞基础功能（题面要求）
  • 每个设计写「反方 / 何时换」——选择有代价，演进有路径（见上表，完整版 README §4）
